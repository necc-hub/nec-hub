## 0. 文档口径与证据规则

### 0.1 四类标记

| 标记 | 含义 | 执行要求 |
|---|---|---|
| **D / Decision** | 本轮已经明确的品牌决策 | 后续物料不得自行反向修改；变更须走品牌评审 |
| **F / Fact** | 本地文件可核对的事实 | 引用时保留来源、日期与适用范围，不自动等同于生产实时状态 |
| **P / Proposal** | 本 PRD 提出的策略、目标或动作 | 批准后排期；未完成前不得对外宣传为既有能力或成果 |
| **M / Measure** | 尚无可靠基线的数据 | D0–D14 完成测量，禁止用估计值冒充实绩 |

### 0.2 对外证据等级

1. **公开可验证**：公开仓库、文档、演示、发布页、真实活动记录。
2. **内部可验证**：评审记录、业务底表、测试报告；对外只能引用经脱敏且获授权的摘要。
3. **规划或目标**：必须写明“计划中”“建设中”“目标”，不得写成“已经实现”。
4. **无法核实的历史数字**：不得进入海报、招商手册、新闻稿和 SEO 结构化数据。

### 0.3 完成定义

品牌工作不能用“稿件已写”代替“用户已形成认知”。本 PRD 按四层验收：

| 层 | 含义 | 证据 |
|---|---|---|
| **S / Strategy** | 策略和口径已批准 | 评审记录、版本号、负责人 |
| **A / Asset** | 资产与页面已完成 | 文案、设计、代码、测试、链接 |
| **P / Publish** | 目标渠道已发布 | 生产 URL、发布时间、实际截图 |
| **V / Validate** | 用户认知或行为达到验收 | 调研、转化、贡献、复访、访谈与队列数据 |

## 1. 执行摘要

### 1.1 核心决策（D）

- **唯一主品牌：NEC。**
- **中文对外标准抬头：常州工 NEC。**
- **英文品牌释义：New Energy Coder。**
- **技术组织标识：`necc-hub` 仅用于 GitHub 组织、代码和工程链接，不作为大众传播主品牌。**
- **Club / Community 作为组织形态或语境描述，不再加入品牌缩写，避免 NEC / NECC 双简称。**
- **品牌精神口号继续沿用：BUILT TO DAWN · 为黎明而造。**

### 1.2 建议战略定位（P）

> **NEC 是“真实工程实践的开源入口”。**

面向希望获得真实项目经验、可验证作品和可复用工程资产的学生与青年工程师，常州工 NEC 提供真实项目、公开代码与文档、工程评审、协作工具和贡献路径，使用户能够从学习走到交付，再把交付沉淀为可被他人复用的公共资产。

### 1.3 建议市场行动句（P）

> **做真实工程，来常州工 NEC。**

它承担“品类解释 + 行动指令”，与情感型品牌口号分工，不替换“为黎明而造”。

| 语句 | 作用 | 主要位置 |
|---|---|---|
| 做真实工程，来常州工 NEC。 | 告诉新用户“你是谁、对我有什么用、下一步做什么” | 官网首屏、招募、活动、招商、视频结尾 |
| BUILT TO DAWN · 为黎明而造 | 表达精神、审美与长期主义 | Logo 组合、KV、PPT 封面、文化内容 |
| KEEP BUILDING | 强调持续构建 | 工程日志、版本发布、贡献者内容 |

### 1.4 首期 90 天必须形成的五项结果（P）

1. P0 对外触点统一为同一套名称、品类描述和 CTA。
2. 建成至少 **3 个可公开核验的旗舰项目证据包**，而不是只有宣传海报。
3. 跑通一条**不依赖校内身份的外部开发者贡献路径**。
4. 建立品牌认知、激活、贡献、复访和推荐的基线与看板。
5. 完成一次“真实工程证据季”战役，用前后测判断认知是否提升，而非只统计曝光。

## 2. 背景、资源与问题诊断

### 2.1 已有资源盘点（F）

| 资源 | 本地可核对内容 | 品牌战略价值 | 使用边界 |
|---|---|---|---|
| 品牌 VI | `public/brand/NEC-VI-Manual_V1.1.md` 已定义 NEC、标志、颜色、字体、KV、PPT 规范 | 已形成可复用视觉资产，不应另起 NECC 品牌 | 需补齐市场定位、话术和生态背书规则 |

| NEC Hub | README 记录门户、应用、Skill、资料、开源仓库、评审、任务、CLA、MCP 等能力 | 是“真实协作与工程过程”的差异化证据，不只是内部工具 | 内部财务、合同、成员和评审信息必须脱敏，不能为宣传开放权限 |
| 开源资产 | GitHub `necc-hub`、Gitee 仓库、文档、Skills、贡献协议与公开签署能力 | 支撑“可查看、可复现、可贡献、可复用” | Star、Fork、仓库数量不能代替实际使用和贡献 |
| 独立项目站 | README 记录擎天塔、MES、SolarGlyph、G-EXO 等项目/应用入口 | 可形成跨机器人、嵌入式、能源和软件的证据矩阵 | 项目状态、效果和合作关系必须逐项核验 |
| 加入流程 | 官网已有申请、介绍、项目分配、开始贡献等路径 | 具备转化流程雏形 | 要分别设计校内成员和外部贡献者路径，避免只进微信群而无任务 |
| 线下场景 | 官网内容包含常州工学院玉衡楼 A416 仓库实验室 | 提供真实工程、设备、活动和人际连接的线下证据 | 不得把场地描述扩大为学校官方背书或未经授权的开放设施 |

### 2.2 当前主要矛盾

1. **名称资产分散**：NEC、NECC、常州工 NEC、New Energy Coder、New Energy Coder Club 等并存。
2. **品类认知发散**：新能源、可持续技术、机器人、嵌入式、编程俱乐部、AI 中台都在表达，但缺少一个能统摄它们的上位品类。
3. **资源多而证据链不完整**：用户能看到项目截图或仓库，却未必能理解问题、过程、结果、复用方法和参与入口。
4. **校内战队与开放社区之间存在解释缺口**：如果外部用户必须依赖校内身份才能参与，“开放生态”就只是一句口号。
5. **加入不等于激活**：加群、填表、关注、Star 与完成首次真实任务之间仍有距离。
6. **缺少心智与队列指标**：曝光、阅读、粉丝等无法回答用户是否知道 NEC 是谁、为何可信、是否再次参与。

### 2.3 核心战略判断

> NEC 当前不缺一个新缩写，也不缺更多零散内容；真正缺的是“一个清晰心智、三组可核验证据、一条低摩擦参与路径、一套持续测量机制”。

### 2.4 用户替代方案与差异化（P）

品牌心智的竞争对象不只是其他学校战队，更是目标用户当前已经使用的替代方案。NEC 不能用“我们也有仓库、教程和社群”建立差异，必须证明以下组合价值：

| 用户现有选择 | 它解决的问题 | 它通常缺什么 | NEC 应证明的差异 |
|---|---|---|---|
| 课程、教程、学习群 | 知识入门和结构化学习 | 缺少真实约束、评审和交付 | 从一项真实任务开始，经历构建、反馈与发布 |
| 代码仓库、模板站 | 获取代码和参考实现 | 缺少场景、维护者、过程与持续响应 | Quickstart + 真实场景 + 维护者 + 可进入的贡献任务 |
| 传统校内竞赛队 | 真实比赛和团队协作 | 参与受身份限制，成果常随赛季结束 | 外部贡献可行，赛季成果转化为长期公共资产 |
| 泛技术社群 | 交流、信息和人脉 | 缺少明确任务、工程结果和作品证据 | 每次参与尽量留下可验证的贡献或作品 |
| 实习、商业项目 | 真实业务与职业经验 | 进入门槛高，过程和成果未必可公开 | 在合规边界内提供可公开学习、复用和署名的工程实践 |

**差异化不是宣称每个功能都独有，而是把“线下真实场景、跨领域项目、工程评审、开放资产、贡献路径”连成一条证据链。** 在外部复现、有效贡献和他人复用尚未形成前，不得把这套组合宣传为已经建立的竞争壁垒。

## 3. 目标、非目标与成功标准

### 3.1 业务目标（P）

- 让 NEC 从“校内团队名称”升级为“发起于常州工学院、可向外部贡献者开放的真实工程实践社区”。
- 让项目成果从一次性比赛/交付材料，转化为可复用代码、文档、Skills、案例和人才成长证据。
- 让合作方从“提供一次资源”升级为“共同提出场景、共同验证、共同发布成果”。

### 3.2 品牌目标（P）

当目标用户产生以下需求时，能够把 NEC 作为优先想到、愿意核验并愿意参与的品牌：

- 我想参与一个真实机器人、嵌入式或新能源工程项目；
- 我想获得可展示、可验证的作品与工程经历；
- 我想找到不仅能看，还能运行、复用和贡献的开源资产；
- 我想寻找一个能把设计、开发、评审、发布串起来的工程协作组织。

### 3.3 用户目标（P）

- 30 秒内听懂：NEC 是谁、和我有什么关系。
- 3 分钟内看到：至少一个真实项目证据和一个可执行入口。
- 30 分钟内完成：一个适合新手的首次价值动作（以具体任务难度为准）。
- 30 天内形成：一次复访、一次有效贡献或一次真实项目协作。

### 3.4 非目标（Non-goals）

- 不追求“所有人都知道 NEC”，先占领明确人群的明确场景。
- 不用 NEC 吞并所有生态项目的独立品牌。
- 不把学校名称用于暗示未经批准的行政背书、官方资质或商业担保。
- 不以购买粉丝、刷 Star、刷下载、互粉群等方式制造虚假增长。
- 不在没有基线时承诺“行业第一”“全国领先”“知名度提升多少”等结果。
- 不为一次改名活动重建所有技术系统、组织和域名。

### 3.5 北极星指标（P）

**月度有效生态用户（Monthly Engaged Ecosystem Users，MEEU）**：

自然月内，去重目标用户在至少两个不同日期完成两类有效行为，且至少一次不是被动浏览。

有效行为包括：

- 成功运行、下载并实际使用公开模板/工具/示例；
- 提交被项目维护者判定为有效的 Issue、复现报告、文档修正或 PR；
- 参加开放构建、评审或 Demo，并完成明确任务；
- 发布基于 NEC 资产的二次作品，并提供可核验链接；
- 与 NEC 完成一个有范围、有交付物的生态共建动作。

**不计入**：页面浏览、点赞、关注、加群、单纯 Star、无后续行为的报名、重复访问、内部测试账号。

### 3.6 首期结果目标（P，D14 冻结最终值）

> 下列为建议目标，不是当前实绩。D0–D14 测得基线 B 后，由评审组冻结 D90 目标；基线为零时报告绝对值，不计算增长率。若认知类基线已高于 75%，不机械追求再增加 15 个百分点，改为缩小重点人群之间的认知差距并保持正确理解。

| 维度 | 指标 | 建议 D90 目标 |
|---|---|---|
| 品牌一致性 | P0 触点名称、首屏品类和 CTA 合格率 | 100% |
| 心智理解 | 接触 NEC 的目标样本中，能正确说出“真实工程实践/开源工程社区”的比例 | 较 B 提升 15 个百分点 |
| 主动访问 | 品牌相关搜索点击或直接访问的有效会话 | 较 B 提升 30% |
| 首次激活 | 外部目标用户完成定义的首次价值动作 | 较 B 提升 25%，同时报告绝对人数 |
| 持续参与 | 激活用户 30 天复访或再次贡献率 | 较 B 提升 10 个百分点 |
| 证据生产 | 完整旗舰项目证据包 | ≥3 个 |
| 外部开放性 | 完成外部路径实测并记录反馈的目标用户 | ≥10 人 |
| 有效贡献 | 外部有效 Issue、文档、测试或代码贡献 | D14 按维护能力冻结，不用 PR 数量单独论功 |
| 数据质量 | 首期活动来源可识别、关键漏斗可复盘 | ≥95% 活动链接带来源；核心事件无重复计数 |

## 4. 生态人群分层与 JTBD

### 4.1 优先级原则

先服务“有明确工程任务和成长动机的人”，再服务泛科技受众。不同人群可以共享 NEC 主品牌，但必须使用不同的价值理由和 CTA。

| 优先级 | 人群 | 核心任务（JTBD） | 当前障碍 | NEC 应占领的心智 | 首要证据 | 第一 CTA |
|---|---|---|---|---|---|---|
| P0 | 校内新手、跨专业学生 | 想入门并做出第一份能展示的真实作品 | 不知从何开始、怕能力不足、只有课程没有项目 | “从第一份真实任务开始，把学习变成作品” | 新手任务、指导路径、真实作品、过程记录 | 查看新手任务并完成一次体验 |
| P0 | 外部开发者、青年工程师 | 想进入机器人/嵌入式/能源场景，找到可复现、可贡献的项目 | 硬件门槛、项目不可复现、贡献无人响应 | “这里能进入真实工程，而不是只围观代码” | 快速开始、Good First Issue、演示、维护者响应 | 运行一个示例或领取一个任务 |
| P0 | 现有队员与项目负责人 | 想提高协作质量，并让成果可复用、可传承 | 文档分散、经验随人走、项目只留结果截图 | “每个项目都要留下公共资产” | 评审记录、文档、Skills、模板、发布记录 | 把一个项目整理成证据包 |
| P1 | 生态项目负责人、其他技术社区 | 想获得工程协作、曝光、贡献者与基础设施，同时保留项目身份 | 担心被主品牌吞并、合作边界不清 | “NEC 是共建网络，不是项目收编方” | 独立项目案例、背书规则、上架与协作流程 | 申请项目上架或联合构建 |
| P1 | 企业、赞助方、雇主 | 想验证工程场景、人才能力和合作产出 | 只有 Logo 曝光、缺少过程和结果证据 | “能看到真实工程过程与可验证成果” | 脱敏评审、Demo、贡献记录、项目复盘 | 查看证据包并提出共建场景 |
| P1 | 教师、导师、竞赛组织 | 想让实践过程可留痕、教学成果可复用 | 课程与项目断裂、成果难沉淀 | “工程教育过程可留痕，成果可传承” | 任务体系、评审方法、案例、模板 | 复用一个教学/训练案例 |
| P2 | 媒体与泛科技用户 | 想理解 NEC 有什么值得关注 | 信息专业、名称易混淆 | “常州工 NEC 做真实机器人与开源工程” | 30 秒介绍、旗舰 Demo、人物故事 | 观看一个案例或参观开放日 |

### 4.2 关键人群洞察

- **新手要的是“能开始”，不是宏大愿景。** 首屏必须给具体任务、预计时间和完成样例。
- **外部开发者要的是“能复现、有人回应”，不是社区人数。** 没有维护者 SLA，就不应大规模导入贡献者。
- **合作方要的是“可验证共同产出”，不是泛泛宣传。** 合作目标应落到场景、资源、交付物和公开边界。
- **生态项目要的是“背书与增量”，不是改名。** 独立项目品牌必须得到尊重。

## 5. 品牌战略屋

### 5.1 品类定义（P）

**首选品类：开源工程实践社区。**

“机器人 × 嵌入式 × 新能源”是重点领域，“开源”是协作方式，“真实工程实践”是用户价值，“作品与资产沉淀”是结果。

### 5.2 品牌使命（P）

> 让学生和青年工程师通过真实工程完成可验证成长，并把每一次实践沉淀为可被他人复用的开放资产。

### 5.3 品牌愿景（P）

> 成为机器人、嵌入式与新能源交叉领域中，值得目标用户优先信任和参与的开源工程实践入口。

愿景不使用“最大”“第一”等无法核验表述。

### 5.4 品牌核心价值（P）

| 价值 | 行为定义 | 反例 |
|---|---|---|
| 真实 | 展示问题、约束、失败、评审和结果，不只展示包装 | 把规划写成成果，把截图写成已上线 |
| 开放 | 公共入口清晰，外部贡献可行，许可与边界明确 | 只有校内身份才能完成所谓开源贡献 |
| 复用 | 项目结束留下代码、文档、模板、Skill 或方法 | 每次新成员都从零开始 |
| 共建 | 贡献者、项目方和合作方共同定义问题与交付 | 只把外部用户当流量或免费劳动力 |
| 长期主义 | 持续维护、版本可追踪、指标可复盘 | 只在招新和比赛前集中造势 |

### 5.5 品牌承诺（P）

> **每一个公开项目，都尽量给用户提供“看得懂、能验证、有入口、可复用”的完整证据链。**

“尽量”不是降低标准，而是允许安全、隐私、第三方许可等边界；无法公开的部分必须说明原因，不能用虚假公开代替。

### 5.6 四大购买理由 / 参与理由（P）

| 理由 | 用户价值 | 必须提供的证据 |
|---|---|---|
| 真项目 | 面对真实约束，不只完成练习题 | 项目背景、对象、周期、角色、演示或交付记录 |
| 真协作 | 有分工、评审、整改和发布过程 | 脱敏任务、评审、版本与贡献记录 |
| 真资产 | 成果能运行、下载、复用和继续贡献 | 仓库、文档、许可证、Quickstart、Skills、模板 |
| 真成长 | 用户能说明自己做了什么、学到什么、留下什么 | 个人贡献、作品、复盘、他人复用记录 |

### 5.7 品牌个性

工程感、清晰、可靠、开放、向上。视觉上延续“工程蓝图 × 破晓地平线”；语言上使用具体动词和可核验事实，减少“赋能、颠覆、领先、生态闭环”等空泛词。

### 5.8 生态增长飞轮（P）

> **真实项目 → 公开证据 → 精准用户 → 首次任务 → 有效贡献 → 可复用资产 → 他人复用与新项目 → 更强的真实证据**

| 飞轮环节 | 必要产物 | 核心责任角色 | 健康指标 |
|---|---|---|---|
| 真实项目 | 明确场景、任务、维护者与当前状态 | 项目负责人 | 可公开核验项目数、维护状态合格率 |
| 公开证据 | 案例、Demo、评审/版本、复盘 | 内容与项目负责人 | 证据包合格率、证据核验率 |
| 精准用户 | 分人群入口与来源识别 | 市场/运营 | 目标人群有效触达，而非泛曝光 |
| 首次任务 | Quickstart、体验任务、Good First Issue | DevRel/维护者 | 首次激活率、首次价值耗时 |
| 有效贡献 | 评审、采纳、合并、整改或共同交付 | 维护者 | 有效贡献率、首次响应时间 |
| 可复用资产 | 代码、文档、模板、Skill、案例 | 项目负责人 | 资产完整度、版本可追踪性 |
| 他人复用 | 二次作品、跨项目复用、共建项目 | 生态负责人 | 有证据的复用次数、新共建项目 |

**飞轮断路即暂停放量**：没有公开证据、没有维护者、外部无法参与、任务没有下一级路径或资产无人复用时，先修复断点，不用增加传播掩盖问题。

## 8. 产品化证据体系：先证明，再传播

### 8.1 旗舰项目证据包（P0）

每个旗舰项目必须形成同一结构，放在官网案例页，并可拆分为视频、推文、海报、招商页和招募材料：

1. **问题**：为谁解决什么真实问题。
2. **场景**：使用环境、用户、限制条件和项目周期。
3. **过程**：关键任务、分工、版本和工程决策。
4. **评审**：至少一次测试、评审、失败或整改记录；可脱敏。
5. **结果**：当前已验证状态，明确区分演示、测试、部署和真实使用。
6. **资产**：代码、文档、模板、Skill、Demo 或硬件资料链接。
7. **复用**：新用户如何运行、下载、二次开发或参与。
8. **人物**：贡献者做了什么，避免只写团队宏大叙事。
9. **下一步**：一个明确 CTA、维护者和响应方式。

### 8.2 首批候选（P，发布前逐项核验）

| 候选 | 推荐承担的认知 | 必须补齐的证据 |
|---|---|---|
| NEC Hub 自身 | NEC 不只讲工程，也用工程方法运营社区 | 公开能力边界、脱敏流程、真实版本、可复用模块、隐私审查 |
| NEC 仓库作业台 / MES | 从实际物资场景到软件交付 | 使用场景、用户角色、操作流程、部署状态、真实问题与改进 |
| 擎天塔 / ROBOCON 项目 | 真实竞赛、跨专业协作和工程实践 | 项目任务、技术路线、评审与版本、可公开资产、比赛结果核验 |
| SolarGlyph 或 G-EXO（备选） | 跨能源/物理智能的项目扩展与生态背书 | 项目归属、维护状态、Demo、可复现程度和外部参与入口 |

### 8.3 证据包上线门禁

- 至少包含一个公开可验证链接、一个过程证据、一个复用入口。
- 所有“已上线、已使用、提升、减少、完成”均有时间、范围和证据。
- 内部成员姓名、头像、合同、财务、飞书 ID、未公开图纸等须授权或脱敏。
- 第三方代码、图片、Logo、许可和合作关系须确认使用边界。
- 页面在桌面与手机实测，无断链、无空白首屏、无错误 CTA。

## 9. 用户旅程与转化漏斗

### 9.1 统一路径

> 看见 → 听懂 → 核验 → 首次价值 → 有效贡献 → 持续参与 → 主动推荐

| 阶段 | 用户问题 | 品牌/产品任务 | 标准动作 | 核心指标 |
|---|---|---|---|---|
| 看见 | 这是什么，和我有关吗？ | 统一抬头和场景，不用抽象口号开场 | 项目短视频、案例摘要、活动海报 | 目标人群有效触达、来源 |
| 听懂 | NEC 到底是战队、俱乐部还是社区？ | 首屏说明“开源工程实践社区 + 重点领域” | 一句话定位、30 秒介绍 | 正确定位识别率 |
| 核验 | 是真实项目还是宣传包装？ | 展示过程、版本、评审与公开资产 | 旗舰证据包、Demo、仓库、文档 | 证据页访问、Demo/Quickstart 点击 |
| 首次价值 | 我现在能完成什么？ | 按人群提供低摩擦任务 | 运行示例、下载模板、报名开放任务 | 首次价值完成率、耗时 |
| 有效贡献 | 我的动作能进入真实项目吗？ | 维护者响应、评审、合并或采纳 | Issue、文档修正、测试、PR、活动任务 | 有效贡献率、首次响应时间 |
| 持续参与 | 下一次为什么还来？ | 任务进阶、反馈、认可和资产复用 | 30 天任务路径、版本更新、贡献记录 | 30 天复访/再次贡献率 |
| 主动推荐 | 我为什么愿意介绍别人？ | 让贡献者获得可展示成果与共同署名 | 个人案例、Demo Day、复用故事 | 有效推荐、二次作品、共同发布 |

### 9.2 外部开发者开放路径（P0）

1. 官网选择“外部开发者”。
2. 查看项目状态、许可证、Quickstart 和维护者。
3. 无需校内飞书账号即可查看公开文档、仓库与 Good First Issue。
4. 完成一个示例或提交一个公开 Issue；需要 CLA 时再进入签署流程。
5. 维护者按 SLA 响应，明确接受、修改或不适合的原因。
6. 合并/采纳后进入贡献记录，优秀案例经本人授权公开。
7. 推荐下一项进阶任务，而不是只邀请进入泛聊天群。

**硬性要求：校内 NEC Hub 登录不得成为外部开源贡献的统一前置条件。**

### 9.3 校内新手路径（P0）

选择方向 → 观看完成样例 → 领取 30–60 分钟体验任务 → 参加介绍/开放构建 → 进入项目组 → 留下第一份可展示成果。

### 9.4 合作方路径（P1）

查看证据包 → 提交场景与资源边界 → 共同定义交付物 → 小规模验证 → 复盘 → 决定是否扩大合作。

### 9.5 响应 SLA（P）

- 表单自动回执：即时，说明下一步和预计时间。
- 人工首次响应：建议不超过 2 个工作日；若官网继续承诺 24 小时，必须保证有人值班。
- Good First Issue 首次维护者响应：建议不超过 3 个工作日。
- 无法及时维护的项目：标明维护状态，暂停大规模招募，不制造无效期待。

### 9.6 开放生态最低治理配置（P0）

“对外开放”必须由仓库和流程证明。每个被重点推广的公共项目至少具备：

- **LICENSE**：明确代码、文档、图片和硬件资料各自适用的许可，不默认全部 MIT。
- **README 与状态**：说明项目解决什么问题、当前处于活跃/维护/暂停/归档哪个阶段，以及演示和复现入口。
- **CONTRIBUTING**：说明任务类型、提交方式、评审标准、CLA/署名要求和维护者响应预期。
- **行为边界**：提供社区行为准则或明确的讨论、协作和反骚扰规则。
- **安全反馈**：提供安全问题联系渠道，不要求用户在公开 Issue 披露敏感漏洞。
- **维护责任**：至少一名维护者；旗舰项目建议另有一名备份，避免单点失联。
- **公开任务**：Good First Issue 有范围、难度、预计投入、完成定义和可获得的反馈。
- **版本与决策**：重要变更通过 Release、公开纪要或决策摘要留痕，内部敏感信息另行脱敏。

项目状态建议统一为：**孵化 / 活跃 / 维护 / 暂停 / 归档**。缺少许可、维护者或基本复现说明的项目不得进入旗舰推广，不得以“开源生态”名义只公开展示截图。

| GitHub / Gitee | 可验证代码与贡献 | Release、Issue、PR、讨论、示例 | 提交有效贡献 |
| NEC Hub | 展示协作能力与沉淀资产 | 公开应用、Skills、资料、CLA | 使用资产/参与开放模块 |
| 微信/社群（已有渠道以实际为准） | 维护关系、活动通知和深度内容 | 案例、活动、周报、复盘 | 报名/领取任务 |
| 视频平台（是否开号另行评审） | 让工程过程可感知 | 60–180 秒 Demo、构建日志、访谈 | 查看完整案例 |
| A416 / 比赛 / 开放日 | 提供真实体验和人际信任 | 开放构建、演示、评审观察 | 完成现场任务 |
| 合作方渠道 | 借用精准信任，不购买泛曝光 | 联合案例、联合 Demo、共建成果 | 进入共建/项目页 |

### 10.3 一源多用，但禁止一键复制

一个项目证据包可拆为：1 个完整案例页 + 1 个 Demo 视频 + 1 篇构建日志 + 1 个 Quickstart + 1 组海报 + 1 次开放活动。不同平台按用户任务重写开头和 CTA，不把同一篇长文机械复制到所有渠道。

### 10.4 最低可持续节奏（P）

- 每周 2 个高质量内容单元：至少 1 个必须是工程证据或可复用资产。
- 每两周 1 次开放构建/答疑，线上优先降低外部参与门槛。
- 每月 1 次 Demo / 贡献复盘。
- 每月更新一次项目维护状态和新手任务清单。
- 无法维护节奏时减少栏目，不用旧闻、伪直播或 AI 批量内容填充。

## 13. 数据测量与品牌心智评估

### 13.1 数据来源

| 数据 | 推荐来源 | 注意事项 |
|---|---|---|
| 品牌搜索与直接访问 | 搜索平台站长工具、官网隐私友好统计 | 区分品牌词、项目词和泛词，记录趋势而非单点 |
| 内容到证据页 | 官网统计、UTM、活动二维码 | 同一用户跨渠道去重规则需说明 |
| 文档与资产使用 | Docs、下载/运行反馈、仓库 Release | 下载不等于使用，需补充成功反馈或后续行为 |
| 贡献 | GitHub/Gitee Issue、PR、文档采纳、CLA | 由维护者标记有效性，拒绝刷量 |
| 活动与加入 | 表单、活动任务、开放构建记录 | 报名不等于到场，到场不等于激活 |
| 复访与持续贡献 | 30 天队列、公开贡献记录、授权后的匿名标识 | 不为追踪而过度收集个人信息 |
| 心智认知 | 前后测问卷、半结构访谈 | 同一人群、同一问题、同一口径 |

### 13.2 品牌调研四问

1. **无提示回忆**：想到“可以参与真实机器人/嵌入式/开源工程项目的组织”，你首先想到哪些？
2. **有提示理解**：你看到的“常州工 NEC”最符合以下哪种描述？（开源工程实践社区 / 单纯比赛战队 / 编程课程 / 软件公司 / 不清楚）
3. **可信证据**：以下哪一项最能让你相信它？（真实 Demo / 公开代码与文档 / 评审过程 / 贡献者作品 / 学校或合作方名称 / 其他）
4. **下一步意愿**：如果继续了解，你最愿意做什么？（运行示例 / 领取任务 / 参加活动 / 提交合作场景 / 暂不参与）

D0 与 D90 使用同一题目。小样本仅作方向性判断；建议每轮目标样本不少于 30 人，并按校内新手、外部开发者等分群报告，不能把小样本外推为全国认知。

首屏发布前另做 **5 秒理解测试**：向目标用户展示首屏 5 秒，随后让其回答“这是谁、提供什么、下一步是什么”。D0–D14 至少覆盖 5 名校内新手和 5 名外部开发者；若多数人仍回答“普通编程俱乐部/比赛战队”或找不到 CTA，先改信息层级，不进入放量阶段。该测试用于发现理解问题，不替代大样本品牌研究。

### 13.3 漏斗指标定义

- **有效触达**：目标人群完成案例/Demo 的有效访问，不含明显机器人和异常流量。
- **定位理解率**：接触后能正确说出 NEC 品类与重点领域的人数 / 有效回答人数。
- **证据核验率**：完成项目证据页、Demo、仓库或 Quickstart 至少一种深度行为的人数 / 有效触达人数。
- **首次激活率**：在约定时间内完成分人群首次价值动作的人数 / 进入对应路径人数。
- **有效贡献率**：贡献被维护者接受、采纳或形成明确整改的人数 / 提交贡献人数。
- **30 天持续参与率**：首次激活后 30 天内再次完成有效行为的人数 / 到期可观察激活人数。
- **推荐率**：带来另一名有效激活用户的推荐人数 / 可观察参与者人数；不得只统计分享按钮点击。

### 13.4 数据降级与去重规则

- 无法跨官网、仓库、表单和活动可靠去重时，**分渠道分别报告，不相加为全网去重用户**。
- 只有匿名聚合数据时，报告会话、事件或可见行为，不包装成确定人数；MEEU 标注为“可观察下限”。
- 只有在用户知情和主动提供关联信息时，才使用经最小化处理的标识连接跨渠道行为；不得为品牌归因额外收集敏感个人信息。
- 30 天留存只统计已经完整经过观察窗口的队列，未到期用户单列，不提前计入成功或失败。
- 基线为零、样本过小或渠道漏报时，保留绝对值和缺口说明，不计算误导性增长率。
- 数据口径变化必须记录生效日期，新旧报告不得直接拼接成连续增长曲线。

### 13.5 反虚荣指标护栏

- 曝光、播放、粉丝、Star 只作为诊断指标，不作为战役成功主指标。
- 不用累计总数掩盖当月无人活跃；同时报告新增、活跃、留存和维护状态。
- 不用大额样本来源不明的问卷宣称“用户心智占有率”。
- 不用学校、合作方 Logo 数量代替真实合作成果。
- 不用 AI 生成内容数量代替工程证据质量。
- 不为追求转化而隐藏项目难度、维护状态或参与成本。

### 13.6 报告节奏

- **周报**：内容、来源、激活、维护者响应和阻塞，一页即可。
- **月报**：品牌一致性、案例质量、MEEU、30 天队列、访谈摘要。
- **D90 复盘**：前后测、目标达成、渠道质量、外部贡献者质量、合作交付、下一季度继续/停止事项。

## 14. 品牌治理与 RACI

### 14.1 角色

| 工作 | 品牌负责人 | 内容/运营 | 项目负责人 | 设计 | DevRel/维护者 | 数据负责人 | 学校/合作接口 |
|---|---|---|---|---|---|---|---|
| 品牌口径与变更 | A/R | C | C | C | C | I | C |
| 旗舰证据包 | A | R | R | C | C | I | C |
| 官网/Hub 发布 | A | C | R | C | C | I | I |
| 开放任务与响应 | I | C | A | I | R | I | I |
| 活动与渠道 | A | R | C | C | R | C | C |
| 数据与前后测 | I | C | C | I | C | A/R | I |
| 隐私、授权与合作边界 | A | R | R | I | C | C | C |

R=执行，A=最终负责，C=会商，I=知会。一个人可兼任多个角色，但每项只能有一个最终 A。

### 14.2 单一事实源

- 品牌战略与口径：本 PRD 及后续批准版本。
- 视觉资产：`public/brand/` 与对应 VI 规范。
- 产品能力状态：README、现行产品 PRD、生产健康信息和真实验收记录。
- 项目证据：项目负责维护的案例页及原始链接。
- 数据口径：品牌指标字典与月度报告。

### 14.3 变更门禁

- 修改 NEC / NECC / 中文抬头 / 英文释义：必须品牌评审。
- 新增项目或合作 Logo：必须项目归属、授权和事实审核。
- 发布“上线、使用、效果、合作”表述：必须有证据和日期。
- 修改域名、GitHub 组织、登录权限：不属于品牌团队单方面决定，另立技术评审。
- 每季度复核一次历史别名和 SEO，不机械全量替换导致搜索资产断裂。

### 14.4 最低资源容量与放量闸门（P）

- 每个旗舰项目至少明确一名维护者；建议配置一名备份，并固定评审与响应时间。
- 每周最多承诺两项高质量内容，优先保证事实核验、Quickstart 和用户反馈，不为日更透支项目团队。
- 品牌负责人、内容、维护者、数据和设计在 D0 评审时确认可投入时段；未确认容量的目标不得写成硬承诺。
- 连续两周达不到已公开响应 SLA，或有效 Issue 持续积压时，暂停拉新和扩大渠道，先处理维护能力与用户反馈。
- 外部路径、隐私授权、证据包和数据基线未通过 P0 验收前，不建议启动付费投放或大规模跨平台推广。

## 15. 风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 学校身份与开放生态冲突 | 外部用户以为只招本校生，贡献必须校内登录 | 使用“发起于常州工学院”；提供独立外部路径和公开任务 |
| 自称社区但仍像内部战队 | 内容只有队员和比赛，外部贡献为零或无人处理 | 公开维护者、任务、SLA、外部贡献案例和治理边界 |
| 定位过宽 | 新能源、机器人、AI、软件什么都讲，用户记不住 | 统一上位品类“真实工程实践”；领域作为项目分类 |
| NEC 搜索混淆 | 搜索结果被其他同名机构占据，用户误认 | 首提固定“常州工 NEC + New Energy Coder + 品类”；积累项目词与品牌词组合 |
| 视觉统一但证据不足 | 海报变多，案例与 Quickstart 没有增加 | 发布门禁要求证据包，先项目后传播 |
| 主品牌吞并生态项目 | 项目方担心失去身份，不愿加入 | 独立项目名 + NEC 背书；明确归属、许可和联合署名 |
| 数据虚荣 | 曝光上涨但激活、复访和贡献不升 | 北极星改为 MEEU，设置反虚荣护栏 |
| 维护者过载 | Issue 无人回、活动后新人流失 | 按维护能力控制招募；标维护状态；先 SLA 后放量 |
| 隐私与授权 | 为展示过程泄露合同、财务、图纸、成员信息 | 脱敏、授权、最小公开、第三方许可检查 |
| 学校/合作方背书夸大 | 对外使用“官方指定、担保”等未经授权表述 | 事实化描述关系，必要时取得书面授权 |
| 商标与商业化风险 | 未来商业产品或付费服务使用 NEC 产生混淆 | 商业化前另做商标、名称与法律检索，本 PRD 不替代法律意见 |
