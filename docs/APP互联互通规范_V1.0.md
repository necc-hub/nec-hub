# NEC HUB APP 互联互通规范 V1.0

> 日期：2026-11-05
> 适用范围：仓内内置应用、`deploy_app` 托管应用、`register_app` 登记的外部应用，以及通过应用广场进入的设备应用。
> 目标：应用不仅能从 NEC HUB 打开，还能在统一身份与权限下共享数据、衔接流程、回传结果。

## 1. “打通”的定义

**打通 = 入口可达 + 身份一致 + 权限一致 + 数据同源 + 流程闭环。**

仅在应用广场登记链接、嵌入 iframe 或完成页面跳转，不算打通。应用也不得通过复制另一应用的私有数据、另建账号体系或只做前端权限隐藏来冒充集成。

打通不代表所有应用都必须开放写操作、集中存储所有数据或各自提供一套 MCP 工具。只读资料页和设备预览页可以按本文声明的边界降级，但必须明确标识能力范围，不能把静态预览描述成实时连接。

## 2. 集成等级

| 等级 | 适用类型 | 必须达到的能力 |
| --- | --- | --- |
| P：公开/只读 | 招募海报、静态资料、归档附件 | 注册入口、返回导航、公开范围声明；不得出现假登录、假实时数据或无反馈的写按钮 |
| I：身份打通 | CLA、域名服务、外部业务系统 | 在 P 基础上复用飞书身份与角色，服务端鉴权，统一处理 401/403 |
| B：业务打通 | 评审、报销、合同、合规、目标、任务等业务应用 | 在 I 基础上使用同源业务数据与统一业务 ID，衔接审批/待办/通知，并能完成至少一条跨应用端到端流程 |
| D：设备打通 | K1 等现实设备应用 | 在 I 基础上经鉴权中继获取实时数据；控制操作默认关闭，开启前必须有独立授权、审计和安全验收 |

内置核心业务应用默认按 B 级验收。新增应用上架时必须声明等级、负责人、数据源、依赖 API、可见范围和验收证据；当前可先记录在应用 README 或上架说明中。

## 3. 统一技术要求

### 3.1 入口与导航

- 应用必须进入 `/api/apps` 合并视图，具有唯一 `name`、明确标题、来源和可见范围。
- 独立页、门户 Tab 与应用广场卡片必须打开同一逻辑应用，不得出现同名应用分叉；R2 覆盖内置应用等例外必须显式提示。
- 分享或刷新深链后仍能到达目标记录；独立页提供返回 HUB 或继续下一流程的明确入口。
- 门户内复用 Vue 组件，不为同一应用复制第二套页面实现；不以 iframe 或 `postMessage` 作为默认集成方式。

### 3.2 身份与会话

- 全队唯一身份键为飞书 `open_id`，展示姓名不能作为权限或关联数据的唯一依据。
- 仓内应用使用 `web/src/shared/auth.ts` 的共享登录态和 `bootAuth`；门户内嵌时使用 `skipAuthBoot`，避免重复 OAuth 兑换。
- 独立页自行初始化共享登录态；门户负责门户级登录引导。`embedded` 只控制展示，不代表已登录。
- 外部应用通过后端调用 HUB 的飞书 OAuth 兑换能力或后续统一 SSO 协议获取身份；`FEISHU_APP_SECRET`、session 密钥和管理 token 不得进入前端。
- 不新建第二套成员账号。确需本地调试账号时只能用于开发环境，不能成为生产业务关联身份。

### 3.3 权限与可见性

- 前端隐藏按钮只用于体验，真正鉴权必须在服务端完成。
- 未登录、无权限、未配置分别返回可识别的 401、403、503，页面给出对应引导，不得白屏或静默成功。
- 财务、审批、设备控制等敏感能力按角色和动作分别授权；不能因为“已打通”而扩大数据可见范围。
- 公开应用必须显式声明公开字段；私有记录不得经公开 API、静态 JSON 或截图链接泄露。

### 3.4 数据与业务 ID

- 每类业务数据只认一个权威来源：审批单走审批引擎及对应底表，任务/目标走既有任务与目标服务，附件走既有 R2 上传链路。
- 跨应用引用使用稳定业务 ID（如评审单号、合同号、报销单号、飞书任务 ID），不得靠标题模糊拼接形成正式关联。
- 门户、独立页、首页组件和 MCP 读取同一记录时，应调用同一服务或同一权威数据源，禁止维护多份可写副本。
- 一端更新状态后，相关视图应在已声明的缓存时效内一致；需要即时一致时必须主动失效缓存或强制刷新。
- 外部系统保留数据主权时，HUB 只保存必要索引与回链，并明确同步方向、冲突规则和失败补偿。

### 3.5 流程、待办与审计

- 业务应用至少打通一条真实闭环，例如“提交 → 审批 → 待办消失 → 状态回写 → 结果可查”。
- 需要他人处理的记录必须进入对应待办或审批视图；完成后应更新原业务记录，不能只发一条群消息。
- 创建、审批、状态变更和外部同步应保留操作人 `open_id`、业务 ID、时间和结果；通知失败不能伪装成业务成功。
- 共用会议、通知、文件上传、MCP 等既有公共服务。不是每个应用都要新增 MCP 工具，但 Agent 能访问的写能力必须服从同一权限边界。

### 3.6 配置与故障降级

- 缺少底表、API 凭证或外部服务时，只降级受影响功能，其他应用仍可使用。
- 配置项和密钥只存既定配置服务或 Wrangler secrets，不写入应用前端、manifest 或仓库。
- 上游超时、限流、无权限必须返回可诊断错误；不得用静态演示数据冒充实时结果。

| `hardware-review` | B | 评审单 ↔ 审批/待办 ↔ 纪要/整改/报告；统一 `HR-*` 单号 |

| 其他公开外链/海报 | P | 明确外链与公开边界，不展示伪造的登录态、实时状态或操作按钮 |

## 5. K1 设备接入专项边界

最新仓内 `k1` 应用只是静态项目预览与局域网入口，当前不满足 D 级。后续打通应按以下顺序实施：

1. 先完成统一身份和只读实时数据中继，由 HUB 或受控服务访问设备，浏览器不直连设备管理端口。
2. 中继接口返回设备在线状态、数据时间和来源；离线或数据过期必须明确显示。
3. 公网页面不得直接创建未鉴权的 `ws://` 内网连接，不做 K1 端口公网映射，不在前端写设备凭证。
4. 查询与控制分离。默认仅开放状态、温度、历史等只读数据；打印、停止、调参等控制必须单独授权、二次确认并记录审计。
5. 局域网入口仅在可达时显示，并提供网络位置提示，不能让公网用户点击后无反馈。

## 6. 上架验收清单

每个应用至少提供以下证据，核心业务应用缺一不可：

- [ ] 已从应用广场进入独立页和门户入口，刷新深链、返回导航均正常。
- [ ] 已用同一飞书账号验证身份一致，无重复登录；外部应用已证明密钥不在前端。
- [ ] 已用队长/组长或财务/普通队员等适用角色验证可见范围，401/403/503 行为正确。
- [ ] 已列出权威数据源、业务 ID、依赖 API、缓存时效和回写方向。
- [ ] 已完成至少一条真实跨应用流程，并核对发起端、待办端、结果端为同一记录。
- [ ] 已验证上游不可用、未配置或同步失败时不会白屏、静默成功或展示假实时数据。
- [ ] 已记录负责人、集成等级、测试日期和验收结果；降级为 P 级的应用已明确标注只读/静态边界。

## 7. 最小端到端验收场景

1. **评审闭环**：从图纸评审提交一单，在审批/待办中处理，回到评审详情和任务排期核对同一单号、状态和负责人。
2. **报销闭环**：提交带附件报销单，在我的报销与审批待办看到同一单据，完成审批/支付后台账和财务汇总按权限更新。
3. **目标闭环**：采纳目标收集单，目标看板出现对应目标，关联任务进度更新后在任务排期和看板中保持一致。
4. **外部身份**：从 HUB 进入 MES，操作人与飞书 `open_id` 一致，无权限操作被服务端拒绝，审计记录可回溯。
5. **K1 只读链路（实装后）**：从 HUB 打开 K1，能区分实时、离线和过期状态；公网不暴露设备端口，普通队员不能触发控制动作。
