# PRD 看板补齐与后续更新清单设计

> 日期：2026-11-22
> 状态：方案 1 已获用户确认
> 范围：`hub.newenergycoder.club/#/prd` 的内容补齐，不扩展业务功能

## 1. 目标与事实边界

在现有 PRD 看板与文档库基础上，补齐代码已交付但页面未收录的内容，并直接回答“接下来还能更新什么”。

页面必须区分：

- **代码已交付**：仓库中存在实现、文档或自动化测试。
- **生产状态**：生产 KV 中已记录的需求状态；不得以本地默认值覆盖或清除。
- **业务已验收**：有真实账号、真实单据或设备的生产证据。单元测试、构建成功和静态预览均不等于业务验收。

## 3. 页面新增“下一步更新”分区

分区位于里程碑看板之后、PRD 文档库之前，使用现有卡片与 VI 样式，不引入新组件库或图表。

采用三列优先级，每项包含关联需求、下一动作和完成证据：

### P0 · 真实业务验收

1. **报销闭环（FE-08 / FE-20）**：带附件提交真实报销，完成审批/支付，核对“我的报销”、台账与财务汇总为同一单据；留存单号、角色、日期与证据。
2. **评审闭环（FE-14～16 / FE-20）**：分别以真实图纸、硬件、合同数据走查提交、审批/会签、整改或纪要、结果回写；图纸继续完成会议/ERP/MES 联调。
3. **身份与待办（FE-01 / FE-09 / FE-17 / FE-18）**：使用队员真实账号复核任务绑定、角色可见范围、48h 待办视角、T-1 标红、目标收集与进度回写。
4. **工作台与权限（FE-02 / FE-11）**：补齐剩余 5 名成员组别，由飞书超管启用定制工作台，并开通审批所需 scope。

### P1 · 功能完善

1. **FE-20 逐应用生产验收**：补共享登录、深链、权限、同源数据及业务 ID 证据；不得用单测或截图替代生产验收。
2. **FE-19 域名服务收尾**：完成真实申请/释放验证；评估 KV 索引并发、到期回收与 DNS 对账。
3. **审批通知卡片灰度**：按流程开启并验证卡片、@ 人和失败回退；卡片内直接审批属于后续独立方案。
4. **K1 安全只读接入**：先做统一身份与鉴权中继，展示在线/离线/数据时间；不公网映射设备端口，不默认开放控制。
5. **任务排期与 CLA 整改**：评审 `localStorage` 数据迁移及 CLA 外部贡献者身份方案，均作为独立变更实施。
6. **RESS 后续迭代**：只有确认真实业务需求后，才增加持久化、报价或审批闭环，并同步数据源与验收证据。

### P2 · 文档与运行治理

1. **专项 PRD 补收与保鲜**：把仓库已有专项 PRD 放入文档库，标明版本、日期和实际状态。
2. **维护白皮书试行**：依据 `docs/NEC网站维护白皮书.md`，逐步补 Owner、复核日期、链接检查与发布/回滚记录；页面不宣称制度已全面生效。
3. **staging 与环境隔离**：评审独立 KV/R2/D1 和测试域名，避免真实验收与公共预览混用生产数据。
4. **状态维护收口**：需求状态继续由 `update_prd` 维护；路线图首版随代码发布，后续明确维护责任，不新增自动推断验收状态的机制。

## 5. 数据流与兼容性

- 继续由 `GET /api/prd` 返回 `milestones`，前端按数据渲染，不改接口路径或卡片结构。
- `DEFAULT_PRD_ITEMS` 只提供无 KV 时的基线；`buildPrdBoard` 继续把生产 KV 合并到默认项，保留 FE-19 的线上覆盖与 `updatedAt`。
- 子项继续挂靠在父卡片，不计入总进度；补齐移动端可展开的子项展示，避免只能“悬停查看”。
- 新路线图为版本化页面内容，不写入生产 KV，不自动触发飞书通知，不执行生产状态变更。
- `/api/prd` 或文档请求失败继续沿用现有错误提示，不显示伪造成功状态。
